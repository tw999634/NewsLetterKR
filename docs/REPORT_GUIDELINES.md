## GitHub Trending 주간 조사 보고서 작성 지침

> **상태:** 관리자 코멘트 반영 중. [2026-11-08 조사 보고서](EXAMPLES.md)를 기준으로 한 작성 지침이다.

### 목적과 적용 범위

- GitHub Trending 주간 목록에서 선정한 프로젝트를 일정한 형식으로 조사해 비교 가능하게 기록한다.
- 이 문서는 **조사 보고서**의 형식이다. [PLAN.md](PLAN.md)의 일본어 뉴스레터 초안·Notion 발행 형식과는 별도로 관리한다. 확인한 내용을 바탕으로 나중에 일본어 기사를 작성한다.
- 원자료를 확인해 작성하고, 확인된 사실과 관심 배경에 대한 추정을 구분한다.

### 파일명과 기본 구조

- 파일명: `github-trending-weekly-YYYY-MM-DD.md`. 날짜는 **수집일(KST)**을 사용한다.
- 제목: `# GitHub Trending 주간 상위 N개 조사 — YYYY-MM-DD`.
- 구성: **수집 시각·기준 → 조사 결과 표 → 순위별 프로젝트 내용**.
- 순위별 상세 내용은 Trending 화면의 순서와 동일하게 배치한다. 주간 Star 증가량이나 전체 Star 수로 임의 재정렬하지 않는다.

### 보고서 상단

| 항목 | 작성 기준 |
| --- | --- |
| 수집 시각 | `YYYY-MM-DD HH:MM KST`로 적는다. 가능하면 UTC도 병기한다. |
| 기준 | 조회한 페이지의 **이름과 URL만** 적는다. 언어 필터 등의 설명을 덧붙이지 않는다. |

### 조사 결과 표

표의 기본 열은 `순위 | 프로젝트 | 주 사용 언어 | Star 수 | 이번 주 증가`로 한다.

- 프로젝트 이름은 `소유자/저장소` 형식으로 쓰고 저장소에 링크한다.
- `Star 수`는 전체 누적 수, `이번 주 증가`는 주간 증가 수로 구별한다. 표기 단위와 쉼표를 통일한다.
- 화면에서 확인할 수 없는 값은 추정해서 채우지 않고 `확인 필요`로 표시한다.
- 표 뒤에 `주 사용 언어는…`으로 시작하는 설명문을 넣지 않는다.

### 프로젝트별 상세 항목

각 프로젝트는 `## 순위. 소유자/저장소` 제목 아래 **프로젝트 개괄 → 화제가 된 이유 → 비고** 순서로 정리한다. 서술형 문단 대신 제목과 하위 요점으로 구성한다.

각 항목 아래에는 **설명 문장 두 개를 하위 bullet list로** 적는다. 결과 보고서에 `쉽게:`, `구체적으로:` 같은 단계 표시를 출력하지 않는다.

1. 첫 번째 bullet: 해당 프로젝트와 업계를 전혀 모르는 사람도 이해할 수 있는 쉬운 설명. 전문 용어가 필요하면 일상적인 말로 뜻을 풀어 쓴다.
2. 두 번째 bullet: 해당 기술의 기초 지식이 있는 사람이 이해할 수 있는 구체적인 설명. 실제 기능, 작동 방식, 관련 수치 또는 사용 조건을 명확히 적는다.

두 bullet은 같은 말을 반복하지 않는다. 첫 번째에서 핵심을 잡고 두 번째에서 기술적 맥락을 더한다.

항목별로 담을 내용은 다음과 같다.

| 항목 | 요점 |
| --- | --- |
| 프로젝트 개괄 | 프로젝트가 무엇을 하고 어떤 문제를 해결하는지 |
| 화제가 된 이유 | 확인 가능한 관심 근거와 주목받는 배경. 추정은 추정임을 알 수 있게 표현 |
| 비고 | 다른 프로젝트와 구별되는 기능, 조건, 최근 변화 또는 특이점 |

`살펴보기`와 별도의 `출처` 항목은 넣지 않는다. 확인에 꼭 필요한 링크가 있다면 해당 요점에 직접 연결한다.

### 조사와 검증 기준

1. 주간 Trending 화면에서 순위, 이름, 주 사용 언어, 전체 Star 수, 주간 증가 수를 확인하고 수집 시각을 기록한다.
2. 각 저장소의 README·공식 문서에서 실제 용도와 주요 기능을 확인한다. 최근 변경을 언급할 때는 릴리스나 변경 기록의 날짜를 확인한다.
3. Trending의 인기 지표를 품질·안정성·실사용 규모의 증거로 표현하지 않는다.
4. 저장소 소개와 README의 수치가 다르면 어느 문서의 값인지 명시하거나 해당 수치를 생략한다.
5. 라이선스, 지원 플랫폼, 설치 방법은 직접 확인한 경우에만 적는다. 확인 시점에 따라 바뀔 수 있는 내용은 날짜나 버전을 함께 적는다.
6. 출처의 문장을 길게 옮기지 않고 자체 요약으로 작성한다.

### 문체와 편집

- 조사 보고서는 **한국어**로 작성한다. 제품명·명령어·파일명은 원문 표기를 유지하고, 처음 나오는 기술 용어는 필요한 만큼 풀어 설명한다.
- 확인된 사실은 단정형으로, 추정은 추정임이 드러나는 표현으로 쓴다.
- 개별 항목은 짧은 요점으로 작성하고, 문단 형태의 장문 설명을 피한다.

### 작성용 골격

```markdown
## GitHub Trending 주간 상위 N개 조사 — YYYY-MM-DD

- **수집 시각:** YYYY-MM-DD HH:MM KST
- **기준:** [GitHub Trending — Repositories / This week](https://github.com/trending?since=weekly)

| 순위 | 프로젝트 | 주 사용 언어 | Star 수 | 이번 주 증가 |
| ---: | --- | --- | ---: | ---: |
| 1 | [owner/repo](https://github.com/owner/repo) | 언어 | 0 | 0 |

### 1. owner/repo

- **프로젝트 개괄**
  - 이 프로젝트는 …을 하는 도구로, …을 쉽게 할 수 있게 한다.
  - …와 …를 이용해 …를 구현하며, 기존에 …했던 작업을 …할 수 있게 한다.
- **화제가 된 이유**
  - 이번 주 많은 관심을 받은 프로젝트로, …과 관련된 문제를 다룬다.
  - 이번 주 … Star 증가가 확인되었으며, … 기능이 관심을 끈 배경으로 보인다.
- **비고**
  - 이 도구를 사용할 때 …을 알아두면 좋다.
  - … 기능은 … 조건에서 제공되며, … 문서에서 확인할 수 있다.
```

### 제출 전 확인

- [ ] 수집 시각을 적고, 기준에는 페이지 이름과 URL만 적었다.
- [ ] 조사 결과 표의 열과 순서가 정해진 형식과 일치한다.
- [ ] 각 프로젝트에 이름, 주 사용 언어, 전체 Star 수, 개괄, 화제가 된 이유, 비고가 있다.
- [ ] 프로젝트별 세 항목에 쉬운 설명과 구체적인 설명을 순서대로 bullet 두 개로 적고, 단계 표시 문구를 출력하지 않았다.
- [ ] 주간 Star 증가량과 전체 Star 수를 혼동하지 않았다.
- [ ] 주요 기능·최근 변경·특이점은 원자료로 확인했다.
- [ ] 확인된 사실과 추정이 구분되어 있다.
- [ ] 표 뒤 언어 설명, `살펴보기`, 별도 `출처`, 뉴스레터 편집 메모를 넣지 않았다.
- [ ] Markdown 링크와 표가 정상적으로 읽힌다.

## GeekNews 조사 보고서 작성 지침

> 앞의 GitHub Trending 보고서 지침의 구조를 GeekNews 기사에 맞게 바꾼 문서다. [2026-11-08 GeekNews 보고서](EXAMPLES.md)를 시범 형식으로 삼는다.

### 목적과 적용 범위

- GeekNews에서 발견한 기술 글을 일정한 형식으로 조사해 한국어 보고서로 기록한다. 일본어 뉴스레터 초안과 발행 형식은 [PLAN.md](PLAN.md)에 따른다.
- 기본 대상은 **GeekNews 첫 화면에 표시된 순서대로 첫 N개 글**이다. `표시 순서`는 인기 순위나 점수 순위를 뜻하지 않는다.
- GeekNews 게시물은 후보 발견과 반응 확인에 사용하고, 내용은 연결된 원문과 필요한 1차 자료로 확인한다.

### 파일명과 기본 구조

- 첫 화면 보고서 파일명: `geeknews-YYYY-MM-DD-first-N.md`. 날짜는 수집일(KST)을 사용한다.
- 제목: `# GeekNews 첫 화면 N개 글 조사 — YYYY-MM-DD`.
- 구성: **수집 시각·기준 → 조사 결과 표 → 표시 순서별 글 내용**.
- 표와 상세 내용은 수집한 화면의 표시 순서대로 놓는다. 점수에 따라 임의로 다시 정렬하지 않는다.

### 보고서 상단

| 항목 | 작성 기준 |
| --- | --- |
| 수집 시각 | 실제 확인한 시각을 `YYYY-MM-DD HH:MM KST`로 적고, 가능하면 UTC도 병기한다. |
| 기준 | 조회한 GeekNews 페이지의 **이름과 URL만** 적는다. 기본값은 `[GeekNews 첫 화면](https://news.hada.io/)`이다. |

### 조사 결과 표

표의 기본 열은 `표시 순서 | GeekNews 글 | 원문 | GeekNews 점수`로 한다.

- **GeekNews 글:** 해당 게시물의 제목 또는 뜻이 분명한 짧은 제목을 적고, GeekNews 게시물에 링크한다.
- **원문:** GeekNews 게시물이 연결한 기사·공식 발표·연구 글·제작자 문서 등에 링크한다. 원문이 여러 개라면 핵심 원문을 표에 넣고 나머지는 관련 요점에 연결한다.
- **GeekNews 점수:** 수집한 화면의 표시값을 적는다. 확인할 수 없으면 `확인 필요`로 표시한다.
- 표시는 **순서**이지 점수 순위가 아니다. 점수와 댓글 수만으로 기사 내용의 정확성이나 뉴스 가치를 판단하지 않는다.
- 접근 제한 또는 웹 조회 자료의 시간차 때문에 화면을 실시간으로 재확인하지 못했다면, 표 아래에 자료의 확인 범위와 한계를 한 문장으로 적는다. 실시간 순위라고 표현하지 않는다.

### 글별 상세 항목

각 글은 `## 표시 순서. 짧은 제목` 아래 **내용 개괄 → 화제가 된 이유 → 비고** 순서로 정리한다. 서술형 문단 대신 항목과 하위 글머리표를 사용한다.

각 항목 아래에는 **표시 문구 없이 설명 문장 두 개**를 하위 글머리표로 적는다.

1. 첫 번째 글머리표는 해당 주제와 기술을 모르는 독자도 이해할 수 있게 핵심을 쉬운 말로 설명한다.
2. 두 번째 글머리표는 기초 지식이 있는 독자를 위해 작동 방식, 확인된 수치, 조건이나 맥락을 구체적으로 설명한다.

두 문장은 같은 내용을 반복하지 않는다. 결과 보고서에 `쉽게:`와 `구체적으로:` 같은 단계 표시를 넣지 않는다.

| 항목 | 담을 내용 |
| --- | --- |
| 내용 개괄 | 글이 다루는 사건·발표·실험·프로젝트와 핵심 변화 |
| 화제가 된 이유 | GeekNews의 확인 가능한 반응과 독자가 관심을 가질 만한 배경. 이유를 확인하지 못했다면 추정으로 표현 |
| 비고 | 공개·시험 단계, 수치의 측정 조건, 적용 범위, 원문 발표일과 GeekNews 게시일의 차이 등 이해에 필요한 사항 |

새로 등록된 글처럼 반응이 아직 적으면 널리 화제가 되었다고 단정하지 않는다. 그 글이 **왜 읽어볼 만한지** 설명하고, 화제성 판단은 이르다고 적는다. 별도의 `살펴보기`·`출처` 항목이나 뉴스레터 편집 메모는 넣지 않는다. 핵심 주장에 꼭 필요한 추가 링크는 해당 글머리표에 직접 연결한다.

### 조사와 검증 기준

1. GeekNews 화면에서 표시 순서·제목·점수를 기록하고, 게시물과 연결된 원문을 연다.
2. 원문의 발행일, 작성 주체, 핵심 주장과 수치를 확인한다. 기사에서 다른 발표·영상·연구를 인용했다면 가능할 때 해당 자료도 확인한다.
3. GeekNews의 한국어 요약과 원문이 다르면 원문을 우선하고, 차이가 중요한 경우 보고서에 명시한다.
4. 제품·프로젝트의 기능은 제작자 문서나 저장소에서, 연구 결과는 논문·실험 원문에서 확인한다. 기자의 관찰이나 회사의 성능 주장은 각각 누구의 주장인지 드러낸다.
5. GeekNews 게시일과 원문 발행일을 구별한다. 오래된 원문이 이번 주에 다시 소개되었다면 새 발표처럼 적지 않는다.
6. 비교 수치는 대상·조건·측정 주체를 확인한다. 같은 조건에서 비교하지 않은 결과를 일반적인 성능 차이로 확대하지 않는다.
7. 원문을 길게 옮기지 않고 자체 요약으로 작성한다.

### 문체와 편집

- 조사 보고서는 한국어로 작성한다. 제품명·기술 용어는 원문 표기를 유지하되, 첫 번째 글머리표에서 이해에 필요한 뜻을 풀어 쓴다.
- 확인된 사실은 단정형으로, 추정은 추정임이 드러나게 쓴다.
- 각 글머리표는 하나의 요점에 집중하고 문단 형태의 장문 설명을 피한다.

### 작성용 골격

```markdown
## GeekNews 첫 화면 N개 글 조사 — YYYY-MM-DD

- **수집 시각:** YYYY-MM-DD HH:MM KST (HH:MM UTC)

### 1. 글 제목

- **내용 개괄**
  - 이 글은 …에 관한 소식으로, …을 알린다.
  - 원문은 … 방식으로 …을 구현·측정했으며, 적용 범위는 …이다.
- **화제가 된 이유**
  - … 문제와 관련되어 독자의 관심을 끌 만하다.
  - GeekNews에서 …점을 받았으며, …이 관심 배경으로 보인다.
```
