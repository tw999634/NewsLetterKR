# 주간 AI 뉴스 웹 수집·분석 시스템 계획

> 상태: 설계안. 현재 코드에는 자동 AI 뉴스 수집기·주간 통합 보고서·일본어 초안 생성 기능이 없다. 기존 `github`·`geeknews` 보고서는 별도 흐름으로 동작한다. 카테고리 기준은 [프로젝트 계획](PLAN.md)에, 관리자 답변과 남은 결정은 이 문서 끝에 정리했다.

## 목표와 산출물

승인된 웹 소스를 정기 조회해 AI 관련 새 발표를 발견하고, 중복 이슈를 묶어 원자료와 날짜·핵심 주장을 대조한다. 집계 기간이 끝나면 **후보 목록 → 한국어 근거 보고서 → 일본어 뉴스레터 초안**을 생성한다. 관리자 승인 전에는 게시하지 않는다.

각 후보에 발견 경로와 원자료를 남긴다. 인기도·추천 수는 발견 신호이며 사실성이나 성능을 증명하지 않는다. 발표 주체의 주장과 독립 확인 결과를 구분한다.

## 주간 7건을 만드는 운영안

관리자 답변에 따라 주간 기준은 **토요일 09:00 KST**, 목표는 **AI 뉴스 7건**이다. 다양한 분야에서 고르고 각 건의 의미와 한계를 원자료 링크와 함께 설명한다. 확인 가능한 후보가 7건보다 적을 때의 예외 처리 방식은 아직 결정해야 한다. 수를 채우려고 오래되거나 근거가 약한 항목을 넣지 않는다. 기사 번호는 편집 순서이며 객관적인 업계 순위가 아니다.

| 시점 | 자동 처리 | 사람이 확인할 것 |
| --- | --- | --- |
| 매일 오전·오후(KST) | 승인된 소스의 새 항목을 조회하고 URL·발표일·발견 시각·원문 링크를 저장 | 새 소스 장애와 접근 제한 알림 |
| 주간 마감 전 | AI 관련 후보를 추리고 같은 발표를 다룬 항목을 하나의 이슈로 묶음 | AI와 무관한 후보, 잘못 합쳐진 이슈 |
| 토요일 09:00 KST 마감 | 직전 마감부터 이번 마감 직전까지의 새 발표·중요한 업데이트를 고정하고 근거 검사를 실행 | 기간 밖 자료의 새 변화 여부와 빠진 주요 소식 |
| 토요일 발행 전 | 근거가 충분한 이슈의 선정표, 한국어 조사 메모, 일본어 초안을 생성 | 기사 채택·순서·표현·출처 승인 |

**후보를 만드는 검색 범위:** arXiv의 AI·기계학습·언어·로봇 분야, Hugging Face의 날짜별 논문, 관리자 감시 목록의 GitHub 릴리스, 승인된 기업·연구기관 발표, GeekNews·Hacker News의 AI 관련 원문 링크. 제품·에이전트, 모델·연구, 로봇, 안전·정책 등으로 분류해 한 분야만 채워지지 않았는지 확인한다. 소스별 관심 지표는 먼저 읽을 후보를 정하는 데만 사용한다.

**선정의 두 관문:** (1) 원자료와 발표·업데이트 날짜가 확인되고 해당 기간에 새 정보가 있어야 한다. (2) 남은 이슈에 독자 관련성, 변화의 크기, 실제 사용 가능성, 근거의 구체성을 각각 `낮음/보통/높음`으로 기록한다. 자동 제안 점수와 함께 선정·보류 사유를 보여주고 최종 7건 안팎은 편집자가 승인한다. 기업 발표의 벤치마크는 발표 주체의 주장으로 표기하며, 실험 결과를 일반적인 성능으로 확대하지 않는다.

기사별 조사 카드에는 최소한 다음을 채운다.

```markdown
### 제목 — 분야
- 이번 주에 새로 나온 것: 발표일·업데이트일, 핵심 변화
- 원자료: 공식 발표·논문·저장소 URL과 확인한 위치
- 핵심 수치: 값, 대상·분모·비교 조건, 발표 주체
- 왜 중요한가: 일본어 독자에게 미치는 영향과 실제 이용 가능 범위
- 한계·미확인: 시험 환경, 미출시 지역, 검증되지 않은 주장
- 선정 상태: 채택 / 보류 / 제외, 담당자와 승인 시각
```

이 카드의 사실 항목을 근거 보고서에 그대로 추적 가능하게 남긴다. 일본어 초안에는 확인된 내용만 반영하고, 원문 링크를 기사 가까이에 둔다.

## 수집 소스와 연결 방식

| 우선순위 | 소스 | 자동 취득 방법 | 쓰임새 |
| --- | --- | --- | --- |
| 1 | [arXiv 메타데이터 API](https://info.arxiv.org/help/api/user-manual.html), [Hugging Face Daily Papers API](https://huggingface.co/docs/huggingface_hub/en/package_reference/hf_api) | 공식 API 어댑터로 AI·ML·언어·로봇 분야의 새 논문 후보를 조회 | 연구 발견. 논문 공개일·개정일과 본문·실험 조건을 별도로 확인 |
| 1 | [GitHub Releases API](https://docs.github.com/en/rest/releases/releases) | 관리자가 승인한 AI 프로젝트·기관 저장소의 릴리스 조회 | 새 버전·기능 발견. 태그만 있는 변경은 릴리스 목록에 포함되지 않으므로 별도 판단 |
| 1 | 기업·연구기관의 공식 발표 | 각 사이트에서 제공하는 피드·API가 있으면 우선 사용하고, 없으면 사이트별 발표 목록 어댑터를 검증해 추가 | 제품·모델·정책 발표의 원자료. 어댑터가 없는 사이트는 수집 누락을 표시 |
| 2 | 기존 [GeekNews RSS](README.md), [Hacker News 공식 API](https://github.com/HackerNews/API) | 기존 RSS 흐름과 공식 API의 새 글·Show HN 목록 조회 | 화제 후보 발견. 기사·프로젝트의 원문에서 핵심 사실 확인 |

관리자가 소스 등록부에 도메인·엔드포인트·방식·조회 주기·대상 범주를 승인한다. 초기 구현에서는 안정된 API·피드부터 시작하고, HTML 구조에 의존하는 사이트는 **각 사이트별 어댑터와 변경 감지 테스트**를 갖춘 뒤 추가한다. 접근 제한을 우회하거나 출처가 불명확한 재게시 자료를 원자료로 취급하지 않는다. 자동 요청은 제공자의 이용 조건과 요청 한도를 확인하고 지킨다. [arXiv API 이용 조건](https://info.arxiv.org/help/api/tou.html), [GitHub REST API 권장 사항](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)을 구현 시 확인한다.

## 처리 흐름

```text
정기 수집 → 후보 정규화·저장 → AI 관련성 분류 → 동일 이슈 묶기
         → 원자료·날짜 확인 → 주장·한계 추출 → 주간 후보 순위화
         → 한국어 근거 보고서 → 일본어 초안 → 관리자 승인
```

1. **수집·정규화:** 소스별 ID·URL·제목·발표 시각·수정 시각·발견 시각·언어와 원자료 위치를 저장한다. URL 정규화, DOI/arXiv ID, 저장소·릴리스 ID로 중복을 찾는다. 원문 전체를 무조건 복제하지 않고 필요한 메타데이터와 근거 위치를 보관한다.
2. **분류·묶기:** 규칙으로 날짜·소스·명백한 AI 키워드를 먼저 거르고, 애매한 후보만 모델이 관련성을 제안한다. 같은 사건의 보도·논문·릴리스는 하나의 이슈로 묶되 서로 다른 발표를 제목 유사성만으로 합치지 않는다.
3. **근거 확인:** 핵심 문장마다 원자료 URL, 근거 위치, 발표 주체, 수치의 대상·분모·측정 조건, 적용 지역·버전을 기록한다. 최초 발표와 후속 업데이트를 구분한다. 모델 출력의 링크·수치·날짜는 원자료 대조에 실패하면 `확인 필요`로 표시한다.
4. **주간 선정:** 관리자에게 확정받은 KST 집계 구간 `[시작, 종료)`에 해당하는 새 발표나 중요한 변경을 대상으로 한다. 독자 관련성·새로움·영향·근거 수준으로 선정 이유를 남긴다. 한 소스의 인기 순서를 전체 AI 뉴스 순위로 전환하지 않는다.
5. **초안 생성:** 승인 전 후보 목록과 한국어 근거 보고서를 만들고, 일본어 초안은 확인된 사실·링크와 한계를 포함해 작성한다. 외부 페이지의 문장은 모델에 대한 지시가 아닌 자료로 취급한다. 원문과 초안의 숫자·제품명·날짜를 다시 대조한다.

## 실행과 데이터 구조

- **일정:** 일정 실행기가 수집기를 하루 단위로 실행하고, 확정된 마감 시각에 주간 집계를 만든다. 재실행해도 같은 소스 항목이 중복 저장되지 않도록 한다. 발행은 별도 승인 단계다.
- **저장:** 처음에는 SQLite에 `sources`, `items`, `events`, `claims`, `runs`, `reviews`를 둔다. 원자료 URL·조회 시각·콘텐츠 해시·처리 상태를 보관해 재검토할 수 있게 한다. 개인정보나 전체 기사 저장은 필요한 범위로 제한한다.
- **장애 처리:** 소스별 성공·실패와 마지막 정상 수집 시각을 기록한다. 일시 오류는 제한된 횟수만 재시도하고, 요청 제한·접근 거부는 해당 소스를 건너뛰며 담당자에게 알린다. 일부 소스가 실패한 주간 보고서는 누락을 명시한다.
- **요청량·비용:** 조건부 요청과 캐시, 소스별 간격·동시성 제한을 적용한다. 모델 호출은 중복 제거 뒤 상위 후보로 제한하고 실행별 호출·비용을 기록한다. API 키는 환경의 비밀 저장소에서 읽는다.
- **기존 코드 연결:** [`report_flow.py`](../newsletter/report_flow.py)의 `github`·`geeknews` 입력과 [README.md](README.md)의 API 계약은 유지한다. 새 주간 AI 파이프라인을 추가하고, 검증 후 CLI·HTTP API에서 별도 보고서 종류로 노출한다. 수집 경로 `source`와 뉴스레터 `category`를 분리한다.

## 개발 단계와 완료 기준

| 단계 | 구현 | 확인할 결과 |
| --- | --- | --- |
| 1. 소스·편집 기준 | 관리자 승인 소스 등록부, KST 마감, 후보·근거 스키마 확정 | 예시 후보의 포함·보류·중복 판정을 재현 가능하게 설명 |
| 2. 자동 수집 MVP | arXiv, 승인된 GitHub 릴리스, GeekNews/Hacker News 중 접근 가능한 공식 경로의 어댑터와 SQLite 저장 | 지정 기간을 재수집해도 중복이 없고 각 소스의 실패·누락이 표시됨 |
| 3. 분석 | 관련성 분류, 이슈 묶기, 원자료 링크·주장·한계 추출, 주간 선정 목록 | 날짜 경계·동일 사건·근거 없는 수치 사례를 검토자가 추적 가능 |
| 4. 보고서·초안 | 한국어 근거 보고서와 일본어 뉴스레터 초안, 관리자 승인 상태 | 모든 발행 후보에 원자료 링크와 승인 기록이 있고 미승인 글은 게시되지 않음 |
| 5. 운영 | 일정 실행, 비용 상한, 소스 장애 알림, 재실행·복구 절차 | 두 번 이상의 주간 시범 실행에서 누락·중복·비용을 확인하고 수정 |

자동 테스트는 수집 응답 표본으로 파서 변경, 날짜·시간대 경계, 중복, 원문 누락, 요청 제한, 보고서 근거 연결을 검증한다. 기존 `github`·`geeknews` 테스트도 유지한다. 외부 사이트가 변하거나 원자료를 확보하지 못하면 자동으로 사실을 채워 넣지 않고 검토 대상으로 남긴다.

## 편집·수집 결정 사항

관리자에게 받은 답변은 다음과 같다.

| 항목 | 답변 |
| --- | --- |
| 주 독자 | 개발자 |
| 주간 집계 기준 | 토요일 09:00 KST. GitHub·GeekNews 등 다른 범주에도 적용 |
| AI 뉴스 발행량 | 호당 7건 목표 |
| 사실 확인 | 발표 자료를 이용해 간결하게 요약할 수 있음. 출처의 주장과 독립 검증은 구분 |
| 산출물 | 기존 GitHub Trending 일본어본 형식을 참고한 일본어 뉴스레터 완성본 |
| 추가 감시 소스 | 진행하면서 추가. 현재 고정 목록 없음 |

다음 정보는 운영 전 관리자에게 더 받아야 한다.

1. 반드시 감시할 기업·연구기관·저장소와 제외할 매체, 유료·로그인 자료의 처리 기준.
2. 한 주에 검증 가능한 후보가 7건보다 적을 때 발행 건수를 줄일지, 발행을 미룰지. 분야별 균형과 기사 순서 기준.
3. 발표일은 기간 밖이지만 기간 안에 큰 업데이트가 있는 자료의 포함 기준.
4. 후보 선정·사실 확인·일본어 완성본·Notion 발행의 승인 담당자와 승인 기록 위치. Notion의 자세한 설정은 [발행 요청 사항](NOTION_ARTICLE_ADMIN_REQUEST.md)에 둔다.
5. 정기 실행 환경(GitHub Actions 또는 Cloud Run Jobs), 장애 알림 담당자, 허용 API·모델 호출 비용과 월간 상한.
6. GitHub·Hugging Face·모델 API 등 필요한 접근 권한과 승인된 비밀 저장 방식.
7. 후보 메타데이터·근거 링크·초안·승인 이력의 보관 기간.
